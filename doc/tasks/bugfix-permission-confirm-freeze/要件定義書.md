# パーミッション変更ダイアログ確定時フリーズバグ 要件定義書

## 1. バグ概要

### 1.1 現象
パーミッション変更ダイアログを開き、パーミッション値を入力してEnterキーで確定すると、アプリケーションが操作不能になる。

### 1.2 影響範囲
- `PermissionDialog`: 単一ファイル/ディレクトリのパーミッション変更
- `RecursivePermDialog`: 再帰的パーミッション変更（ディレクトリに対して「Recursively」を選択した場合）

### 1.3 関連する過去のバグ修正
コミット `c8fbfeb` にて、Escキーでダイアログをキャンセルした際のフリーズバグが修正済み。今回のバグは同じパターンだが、確定（Enter）時に発生する。

## 2. 再現手順

### 2.1 PermissionDialogの場合
1. duofmを起動
2. 任意のファイルまたはディレクトリを選択
3. `p`キーを押してパーミッション変更ダイアログを開く
4. 3桁の8進数パーミッション値を入力（例: `644`）
5. Enterキーを押して確定
6. **期待動作**: パーミッションが変更され、ダイアログが閉じ、通常操作に戻る
7. **実際の動作**: アプリケーションがフリーズし、キー入力を受け付けなくなる

### 2.2 RecursivePermDialogの場合
1. duofmを起動
2. ディレクトリを選択
3. `p`キーを押してパーミッション変更ダイアログを開く
4. Tab/Spaceキーで「Recursively (all contents)」を選択
5. 3桁の8進数パーミッション値を入力してEnter（ステップ1: ディレクトリ用）
6. 再度3桁の8進数パーミッション値を入力してEnter（ステップ2: ファイル用）
7. **期待動作**: 再帰的にパーミッションが変更され、通常操作に戻る
8. **実際の動作**: アプリケーションがフリーズ

## 3. 根本原因分析

### 3.1 問題のメカニズム

duofmのダイアログシステムでは、`Model.dialog`フィールドにダイアログ参照が格納される。キー入力は`handleKeyInput`関数で処理され、ダイアログが存在する場合はダイアログに委譲される：

```go
// internal/ui/model_update_keyboard.go
func (m Model) handleKeyInput(msg tea.KeyMsg) (tea.Model, tea.Cmd) {
    // ダイアログが開いている場合はダイアログに処理を委譲
    if m.dialog != nil {
        var cmd tea.Cmd
        m.dialog, cmd = m.dialog.Update(msg)
        return m, cmd
    }
    // ...
}
```

### 3.2 フリーズの原因

`PermissionDialog.Update`メソッドでEnter押下時の処理:

```go
// internal/ui/permission_dialog.go
case tea.KeyEnter:
    // バリデーション
    if err := fsops.ValidatePermissionMode(d.inputValue); err != nil {
        d.errorMsg = err.Error()
        return d, nil
    }
    d.Close()  // ダイアログを非アクティブ化
    if d.onConfirm != nil {
        recursive := d.recursiveOption == 1
        return d, d.onConfirm(d.inputValue, recursive)  // コールバック実行
    }
    // ...
```

**問題点**:
1. `d.Close()`は`d.active = false`を設定するだけ
2. `onConfirm`コールバックは`permissionOperationCompleteMsg`を返す
3. `handlePermissionOperationComplete`では`m.dialog = nil`を設定していない

これにより、ダイアログは非アクティブだがModel.dialogには参照が残り続ける。非アクティブなダイアログの`Update`メソッドは:

```go
func (d *PermissionDialog) Update(msg tea.Msg) (Dialog, tea.Cmd) {
    if !d.IsActive() {
        return d, nil  // 何もせずに戻る
    }
    // ...
}
```

後続のキー入力はすべてこの非アクティブなダイアログに委譲され、無視され続けるためフリーズする。

### 3.3 過去の修正との差異

コミット`c8fbfeb`では、Escキーでのキャンセル時に`permissionDialogCancelMsg`を送信するようになった:

```go
case tea.KeyEsc:
    d.Close()
    return d, func() tea.Msg {
        return permissionDialogCancelMsg{}
    }
```

そして`handlePermissionMessages`でこのメッセージを処理して`m.dialog = nil`を設定:

```go
if _, ok := msg.(permissionDialogCancelMsg); ok {
    m.dialog = nil
    return m, nil, true
}
```

しかし、確定時の処理では`handlePermissionOperationComplete`が呼ばれるが、そこで`m.dialog = nil`が設定されていない。

## 4. 修正要件

### 4.1 機能要件

#### FR1: PermissionDialogの確定時処理
- **FR1.1**: パーミッション変更操作が完了した後、`m.dialog`を`nil`に設定すること
- **FR1.2**: 成功・失敗に関わらずダイアログ参照をクリアすること
- **FR1.3**: ダイアログクリア後、通常のキーボード操作が正常に機能すること

#### FR2: RecursivePermDialogの確定時処理
- **FR2.1**: 再帰的パーミッション変更操作が完了した後、`m.dialog`を`nil`に設定すること
- **FR2.2**: エラーレポートダイアログを表示する場合を除き、ダイアログ参照をクリアすること
- **FR2.3**: エラーレポートダイアログ表示時は新しいダイアログを`m.dialog`に設定

#### FR3: バッチパーミッション変更の確定時処理
- **FR3.1**: バッチパーミッション変更操作が完了した後、ダイアログ参照を適切に管理すること
- **FR3.2**: プログレスダイアログからエラーレポートダイアログへの遷移を正しく処理すること

### 4.2 非機能要件

#### NFR1: 既存機能への影響なし
- キャンセル時のフリーズバグ修正（c8fbfeb）に影響を与えないこと
- 他のダイアログ（ErrorDialog, HelpDialogなど）の動作に影響を与えないこと

#### NFR2: コード一貫性
- 過去のキャンセル時バグ修正と同様のパターンを適用すること
- ダイアログ完了メッセージ処理のベストプラクティスに従うこと

## 5. テスト要件

### 5.1 単体テスト

#### UT1: PermissionDialog確定時テスト
- Enterキー押下時に適切なメッセージが返されることを確認
- 無効な入力時はエラーメッセージが設定されダイアログが閉じないことを確認

#### UT2: RecursivePermDialog確定時テスト
- ステップ1（ディレクトリ権限）からステップ2（ファイル権限）への遷移を確認
- ステップ2完了時に適切なメッセージが返されることを確認

### 5.2 結合テスト

#### IT1: ダイアログ確定フロー統合テスト
- パーミッション変更完了後に`m.dialog`が`nil`になることを確認
- 完了後にキーボード操作（j/k等）が正常に機能することを確認

#### IT2: 連続操作テスト
- 1つ目のファイルでパーミッション変更確定後、2つ目のファイルで再度ダイアログを開けることを確認

### 5.3 E2Eテスト要件

#### E2E1: ダイアログ確定後の挙動確認
- パーミッション変更ダイアログを開く
- パーミッション値を入力してEnterで確定
- ダイアログが閉じることを確認
- ファイル一覧でカーソル移動（j/k）が機能することを確認
- ステータスバーに成功メッセージが表示されることを確認

#### E2E2: 再帰的パーミッション変更後の挙動確認
- ディレクトリを選択してパーミッションダイアログを開く
- 再帰オプションを選択
- 2段階のパーミッション入力を完了
- ダイアログが閉じ、通常操作に戻ることを確認

#### E2E3: エラー発生時の挙動確認
- 書き込み権限のないファイルでパーミッション変更を試行
- エラーメッセージが表示されることを確認
- ダイアログが閉じ、通常操作に戻ることを確認

#### E2E4: バッチパーミッション変更後の挙動確認
- 複数ファイルをマーク
- パーミッション変更を実行
- プログレスダイアログが表示され、完了後に閉じることを確認
- マークがクリアされ、通常操作に戻ることを確認

## 6. 実装ガイドライン

### 6.1 修正箇所

1. **`internal/ui/model_permission.go`**:
   - `handlePermissionOperationComplete`: `m.dialog = nil`を追加
   - `handleRecursivePermissionComplete`: エラーレポートダイアログを表示しない場合に`m.dialog = nil`を追加
   - `handleBatchPermissionComplete`: プログレスダイアログクリア処理を確認（既に実装済みの可能性）

### 6.2 テストファイル

1. **`internal/ui/dialog_integration_test.go`**:
   - 確定時の統合テストを追加（既存のキャンセルテストと対になるもの）

### 6.3 E2Eテスト

1. Chrome DevTools MCPを使用したE2Eテスト
   - ダイアログ確定後の画面状態確認
   - キーボード操作の応答確認

## 7. 影響分析

### 7.1 影響を受けるファイル
- `internal/ui/model_permission.go`: メッセージハンドラー修正
- `internal/ui/dialog_integration_test.go`: テスト追加

### 7.2 影響を受けない機能
- パーミッション変更のコアロジック（`internal/fs/`）
- ダイアログUI自体（`permission_dialog.go`）
- 他のダイアログの動作

## 8. リスク評価

### 8.1 低リスク
- 修正は1行程度（`m.dialog = nil`の追加）
- 既存のキャンセル時修正パターンに従う
- 影響範囲が限定的

### 8.2 考慮事項
- エラーレポートダイアログへの遷移ケースでは`m.dialog`を上書きするため、クリアは不要
- バッチ操作完了時のダイアログクリアが既に正しく実装されているか確認が必要

## 9. 完了基準

1. パーミッション変更ダイアログで確定後にフリーズしないこと
2. 再帰的パーミッション変更ダイアログで確定後にフリーズしないこと
3. バッチパーミッション変更完了後にフリーズしないこと
4. 既存のキャンセル時動作が正常に機能すること
5. 結合テストが全てパスすること
6. E2Eテストでダイアログ閉鎖後の操作が確認できること
