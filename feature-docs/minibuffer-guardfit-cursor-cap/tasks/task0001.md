# Task Plan: task0001 — Keep the cursor visible when guardFit reaches its re-measurement cap

## Goal

When the minibuffer's width-fitting guard gives up because it reached its
re-measurement cap, View narrows the displayed input to the cursor alone and
shows it whenever that line fits the content width; only when the cursor
alone does not fit are input and cursor both hidden. Regression tests for all
three input-window paths make a recurrence fail.

## Requirements

FR1, FR2, FR3, FR4, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `internal/ui/minibuffer.go` — failure handling after guardFit in View's three input-window paths (cursor-only fallback with one extra measurement); guardFit's result may be extended if the chosen design needs it
- `internal/ui/minibuffer_test.go` — View-level regression tests for the three paths and for the cursor-alone-does-not-fit case

## Design

### Terms

- **Content width**: m.width - 4 (the minibuffer style's inner width).
- **Width basis**: the display-width measurement View and guardFit already
  use for assembled lines. No other width source is introduced (SPEC a5).
- **Window**: the rune range of the input View displays, plus its highlight
  (the cursor's whole grapheme cluster as one reversed segment, or the
  trailing block cursor when the cursor is at the end).
- **Cursor alone**: a window that contains only the cursor's grapheme
  cluster (highlighted), or, when the cursor is at the end, no input runes
  and only the trailing block cursor.
- **The three input-window paths** (SPEC FR1):
  - P1, cursor at the end: the block cursor sits at the right edge; whole
    grapheme units are trimmed from the front.
  - P2, cursor inside the input and the whole before-cursor segment fits:
    after-cursor units are trimmed from the back first, then before-cursor
    units from the front.
  - P3, cursor inside the input and the before-cursor segment does not fit:
    the cursor's grapheme sits at the right edge; before-cursor units are
    trimmed from the front.

### Defect being fixed

guardFit reports "does not fit" in two different situations:

- (a) Cap reached: the re-measurement cap (3 re-measurements after the
  first measurement) is hit while the window still holds units other than
  the cursor.
- (b) Exhausted: the path's shrink step can remove nothing more, i.e. the
  window already is the cursor alone.

Today every path treats both the same way and hides input and cursor. Only
(b) shows that the cursor alone does not fit; in (a) a cursor that would fit
alone disappears.

### Invariant relied upon

When guardFit reports "does not fit", its last measurement was of the
window in its current state: after the final measurement at the cap it does
not call shrink again, and a shrink that reports "nothing more to remove"
leaves the window unchanged. So in situation (b) the cursor-alone line has
already been measured and did not fit.

### New failure handling (identical in P1, P2 and P3)

1. guardFit reports "fits": display that window (unchanged behavior).
2. guardFit reports "does not fit" and the window already is the cursor
   alone (P1: no input unit kept before the block cursor; P2: no
   after-cursor unit and no before-cursor unit kept; P3: no before-cursor
   unit kept): render neither input nor cursor (FR2). No extra measurement.
3. Otherwise (situation (a)): narrow the window to the cursor alone (P1:
   empty input range with the trailing block cursor; P2 and P3: exactly the
   cursor's grapheme cluster, highlighted as one reversed segment).
4. Assemble the prompt followed by that cursor-alone window, in exactly the
   way View assembles its final line, and measure it once with the width
   basis (NFR2).
5. If that width is at most the content width, display that line (FR1).
   Otherwise, render neither input nor cursor (FR2).

The flow is the same in all three paths. It may be shared by one helper or
repeated per path, whichever reads more clearly next to the existing code.
Do not split View only to make it testable (FR4).

### Contracts

- **Measured equals displayed**: the line measured in step 4 is exactly the
  line View outputs for that outcome (same prompt, same window, same
  highlight). The width check then holds for the line the user sees.
- **Telling (a) from (b)**: this may be decided from the window state as in
  step 2, or guardFit may report which situation stopped it. Either way:
  - the prompt-truncation path (prompt width at least the content width)
    keeps its current outcome, where any "does not fit" ends in an empty
    prompt (FR3, SPEC a2);
  - the cap stays at 3 re-measurements after the first (SPEC a1);
  - each View call makes at most one width measurement beyond guardFit's
    own (NFR2, TM-1).
- **Unchanged branches** (FR3): the step that shows prompt and whole input
  untruncated when they fit; the branch that renders no input when the
  cursor's grapheme alone is wider than the remaining width; the content
  width <= 0 branch (m.width 0-4: no panic, no line break); the
  prompt-truncation branch.
- **Postcondition** (FR3): for m.width > 4, the output contains no line
  break and its display width is at most m.width - 2.

## Test Notes

- All new tests are unit tests in internal/ui/minibuffer_test.go. They go
  through View only (SPEC FR4).
- **Red first**: AC-1 to AC-3 must fail against the unmodified View,
  because the cursor disappears. A fixture that already passes before the
  change does not reach the cap. Replace it with an input that has the same
  property (at the prompt boundary, the width estimate is smaller than the
  measured width), as SPEC a3 allows, and state the substitution in the
  test's comment.
- **Premise checks**: follow the existing checkVS16Premises pattern and
  check premises fatally before any other assertion, so fixture drift is
  never mistaken for a regression. For example:
  - the prompt plus the whole input does not fit the content width;
  - for AC-1 to AC-3, the prompt plus the cursor-alone line fits the
    content width;
  - for AC-4, the prompt plus the cursor-alone line, assembled the way View
    assembles it under that test's color profile, is wider than 6.
- **AC-4 color profile**: SPEC TS4 runs under a profile that emits no
  style sequences. Under that profile the cursor grapheme sits directly
  after the prompt's U+0600 and measures together with it. Fix that
  profile explicitly for the test and restore the previous one at cleanup,
  like fix256ColorProfile does. The profile is process-global, so do not
  run these tests in parallel. Under this profile reversedRuns is always
  empty. The main evidence is that no input rune appears in the visible
  output.
- **AC-1**: assert the reversed run on the end path. SPEC FR4 makes this
  mandatory.
- **SPEC edge cases worth covering if they come out naturally**: the cursor
  on a rune in the middle of a cluster (the whole cluster is still one
  reversed run); a 2-column cursor grapheme whose width exactly equals the
  width left for input; shrink running out before the cap is reached (the
  AC-4 behavior).
- **Optional (SPEC a3)**: an internal test that pins the re-measurement
  count is allowed but not required. It must not need a test-only hook in
  production code (NFR1).
- Commands: test_command and format_command in workflow.yaml
  project.components.duofm.
