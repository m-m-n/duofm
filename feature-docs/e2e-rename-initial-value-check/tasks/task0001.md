# Task Plan: task0001 — Input-line-only initial-value checks for the rename E2E tests, and removal of the always-passing history check

## Goal

The two rename E2E tests verify the rename dialog's input-field initial value
with a check that only the input field row can satisfy, so a wrong initial
value (empty, or the full name with extension) makes them fail. The
always-passing `testdata` check in `test_history_forward_cleared` is removed.

## Requirements

## Design

### Screen facts the check relies on

From SPEC.md A-1 and the dialog's rendering (to be confirmed against an
actual capture, see "Layout confirmation" below):

- The extension-preserving rename dialog draws the input field as a
  three-row box with a rounded border. Its middle row holds, left to right:
  the box's left vertical border (`│`), one padding column, the input content
  (the base name only), whitespace fill, the box's right vertical border
  (`│`), one separating space, and the fixed extension (`.txt`). The
  extension is vertically centered against the three-row box, so it sits on
  that same middle row.
- The dialog title (`Rename (extension: .txt):`) is on a different row.
- The screen capture used by the E2E helpers is plain text: colors and
  reverse video are dropped, so a cursor drawn only by reverse video appears
  as the underlying character or as a space.
- How the text input component's cursor appears in the capture is
  unconfirmed (SPEC.md A-2). The check must not depend on it.

### Input-line check (one helper, used by both rename tests)

A single helper defined inside `file_operation_tests.sh`. FR2 requires the
same method as FR1, so both call sites use this one helper.

| Item | Contract |
|------|----------|
| Inputs | session identifier; expected base name; fixed extension; human-readable description |
| Precondition | the extension-preserving rename dialog is open in the session |
| Pass condition | the screen is captured once; each captured row is examined on its own (a match never spans two rows); the check passes if and only if at least one row contains, in this order: (1) a vertical border character, (2) only whitespace, plus at most one cursor glyph immediately before the base name, (3) the expected base name, (4) at most one cursor glyph immediately after the base name, then only whitespace, (5) a vertical border character, (6) only whitespace, (7) the extension |
| Literal matching | the base name and the extension are matched as literal text: `_` and `.` carry no pattern meaning (the `.` of `.txt` must not match an arbitrary character) |
| Cursor glyph | any single non-whitespace character (whatever the cursor looks like). A multi-byte glyph (for example a block character) counts as one character regardless of the E2E container's locale |
| Counting | counts exactly one check: the run counter increases by one, and exactly one of the passed / failed counters increases by one |
| Output | prints the pass / fail line with the description in the same style as the helpers in `helpers.sh`; on failure also prints the expected base name and extension and enough of the captured screen to include the dialog rows (not only the first 10 rows) |
| Return status | success on pass, failure on fail, like the existing assertions |

Consequences of the pass condition (these are the SPEC.md edge cases):

- Empty initial value: no row holds the base name between the borders → fails.
- Full name with extension (`before_rename.txt`): after the base name comes
  `.txt` (more than one non-whitespace character before the right border) →
  fails.
- The file-list row `before_rename.txt` / `navren_before.txt`: the base name
  is followed by `.txt` with no border in between → never matches, whether
  the row is visible or hidden behind the dialog.
- The search-filter display (`/before_ren`, `/navren_before`): not framed by
  the border pair followed by the extension on the same row → never matches.

Naming and placement constraints:

- The helper's name must not start with `test_`. The runner
  (`run_all_tests.sh`) treats every line beginning with `test_` in
  `tests/*.sh` as a test definition; such a name would be executed as a test
  by the category runner and reported by the run-list guard (SPEC.md A-4: no
  test functions are added).
- The name must not collide with any function in `helpers.sh` or in other
  `tests/*.sh` files: a full run sources every test file into one shell.
- `helpers.sh` is not edited (NFR2). The helper lives only in
  `file_operation_tests.sh`.

### Call sites

- `test_rename_file`: the initial-value check uses the helper with base name
  `before_rename`, extension `.txt`, and the existing description ("Rename
  dialog is pre-filled with the base name"). The title check before it
  (`Rename (extension: .txt):`) stays as is.
- `test_navigation_after_rename`: same, with base name `navren_before`.
- Every other step of both tests (clearing with `C-u`, typing the new name,
  Enter, the on-disk checks, the quit check, cleanup) is unchanged. The
  comment above each check may be updated to say the check is limited to the
  input field row.

### history_tests.sh

- In `test_history_forward_cleared`, the `assert_contains "testdata"` call
  (both of its lines) is removed.
- The `assert_not_contains "/testdata/dir1"` call ("[ key leaves directory A
  (dir1)") stays directly after the `[` key press and its wait.
- The comment before the `[` key press may stay; it still describes the
  step.

### Layout confirmation (SPEC.md A-2)

Before settling the pass condition, capture the dialog's screen once in the
E2E container, using a temporary change that is not committed. Confirm the
border character, that the extension is on the input row, and how the cursor
appears. Record what was observed in the implementation report. If the
observed layout differs from "Screen facts" above, adapt the anchors to the
observed input row. The matched structure must still be one that no
file-list row, the title row, or the search-filter display can produce.
Report the difference as a plan deviation. Never fall back to a bare
base-name match.

## Test Notes

- The deliverable is test code, so the TDD red / green pair is: red = the
  mutation runs (AC-2, AC-3) show that the new check fails on a wrong
  initial value; green = the unmodified run passes (AC-5). Record the
  mutation results (which checks failed) in the implementation report. The
  mutations themselves are never committed.
