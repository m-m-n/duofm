# Task Plan: task0003 — Anchor the input-field assertion to the dialog row's structure

## Goal

The file-local input-field value assertion in `file_operation_tests.sh`
identifies the input field's own left and right borders from the structure of
the whole dialog row, so a border character (`│`) inside the input value can
never serve as either border. Both rename tests' initial-value checks then
fail when the input field holds any extra non-whitespace character before or
after the base name, including `│` (`x│before_rename`, `│before_rename`,
`before_rename│ .txt`, and the same for `navren_before`).

## Requirements

FR1, FR2, NFR1, NFR2

  helper's comment to state exactly what the new pass condition guarantees.

## Design

The assertion's contract is IMPLEMENTATION.md "Input-field value assertion
contract" and decision D2. Its Strictness and Required-outcomes rows already
require rejecting every extra non-whitespace character next to the base name.
The merged pass condition does not meet them: the match is unanchored, so any
`│` in the row that is followed by whitespace and the base name can act as the
input field's left border, including a `│` that is part of the input value.
This task closes that gap. Nothing outside the assertion changes.

- **Observed input row**: a real E2E screen capture of the dialog shows the
  input row as
  `        │  │ before_rename                     │ .txt     │` —
  leading whitespace, the dialog's left border, whitespace, the input field's
  left border, one space of padding, the value, padding, the input field's
  right border, one space, the extension, padding, the dialog's right border.
  Before changing the pattern, the implementer confirms this structure against
  a real capture (for example from a TS-1 run). If the real row differs, the
  anchoring follows the observed structure while keeping the guarantee below.
- **Pass condition (new)**: at least one captured row matches the whole row
  structure, anchored at the row's start and at the row's end: only
  whitespace, the dialog's left border, only whitespace, the input field's
  left border, only whitespace, the base name, only whitespace, the input
  field's right border, only whitespace, the extension, only whitespace, the
  dialog's right border, only whitespace to the end of the row.
- **Guarantee**: every `│` on a passing row is at one of the four structural
  positions above, and the only non-whitespace text between the input field's
  two borders is the base name. A `│` typed into the value before or after the
  base name therefore makes the row fail.
- **Whitespace**: the amount of whitespace at each "only whitespace" position
  is not fixed. Extra whitespace-only characters around the base name stay
  outside the check's scope (SPEC A-6).
- **Unchanged**: literal matching of the base name and the extension (ERE
  metacharacters escaped), the forced UTF-8 locale for the match, one row per
  match, the assertion's name, its positional inputs, the two call sites and
  their arguments (`before_rename` / `.txt`, `navren_before` / `.txt`), the
  one-check-per-call counting, the pass / fail output lines, and the return
  status. Every other step of `test_rename_file` and
  `test_navigation_after_rename` is unchanged.
- **Comment**: the helper's comment describes the anchored structure and states
  only what the pattern enforces: a border character inside the input value
  cannot act as either input-field border, and whitespace-only extras are out
  of scope. It does not claim uniqueness beyond what the anchored structure
  enforces.
