# Task Plan: task0001 — Add VS16 emoji regression tests for minibuffer View

## Goal

Add regression tests to `internal/ui/minibuffer_test.go` that fail if the
minibuffer again underestimates the display width of VS16 (U+FE0F) emoji
sequences, on both the input side and the prompt side. After this task, the
minibuffer's single-line rendering and its displayed content under the
reproduction condition are guaranteed by tests. The production code is not
changed.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify
- `internal/ui/minibuffer_test.go` — add the regression tests and the two test-local helpers described in Design

## Design

### Subject under test (unchanged)

The minibuffer component's public contract used by the tests: set prompt,
set width (m.width), set input (moves the cursor to the end), set cursor
position (clamped to 0..rune count), show, and render (View). The rendered
result is one styled line whose content width is m.width-4 and whose total
display width must stay at most m.width-2 without a line break. The
implementation file `internal/ui/minibuffer.go` is not modified by this
task (NFR1).

### Fixtures

| Name | Value | Premise value (FR3 / FR5) |
|------|-------|---------------------------|
| P-JA | prompt `(reverse-i-search)'日本語': ` | display width 28 |
| PAIR | U+2764 U+FE0F (HEAVY BLACK HEART + VARIATION SELECTOR-16) | display width of the pair 2; sum of the two runes' own display widths 1 |
| IN-4 | PAIR repeated 4 times (8 runes) | — |
| P-VS | prompt `(reverse-i-search)'` + PAIR repeated 4 times + `': ` | display width 30 |

All widths are measured with the same width basis as the existing helper
assertBoundedSingleLine (the project's single width basis for the
minibuffer).

Reference facts for the expected values: at m.width 37 the content width is
33 and the remaining width after P-JA is 5, so the cursor-at-end path keeps
two pairs (28 + 4 + 1 cursor block = 33). With P-VS at m.width 29 the
content width is 25, so the prompt-truncation path keeps
`(reverse-i-search)'` (19 columns) plus three pairs (6 columns).

### Existing helpers (used as-is, not modified or moved)

- assertBoundedSingleLine (this file): reports a line break or a display
  width above m.width-2.
- mustNotPanic (defined in `pane_render_test.go`, same test package): runs
  the render and reports a panic as a test failure.
- stripANSI (defined in `model_view_test.go`, same test package): removes
  ANSI escape sequences for content assertions.

### New test-local helpers

| Helper | Responsibility | Contract |
|--------|----------------|----------|
| Premise check | Verify the fixture premises before any assertion | Pre: none. Post: returns normally only when P-JA width is 28, PAIR width is 2 and PAIR's per-rune width sum is 1 (plus P-VS width 30 when the caller asks for the P-VS premise); otherwise stops the test immediately (fatal) with a message naming the premise, the expected value and the observed value. |
| Pairing check | Detect a split VS16 pair in visible text | Pre: input is ANSI-stripped visible text. Post: reports a non-fatal test error when any U+2764 is not immediately followed by U+FE0F, or any U+FE0F is not immediately preceded by U+2764; reports nothing otherwise (including text that contains neither rune). |

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR3): Every added test first runs the premise check — P-JA display width 28, PAIR display width 2, PAIR per-rune width sum 1, and additionally P-VS display width 30 in the P-VS tests — and stops immediately with a fatal failure naming the drifted value when any differs.
- [ ] AC-2 (FR1): With P-JA, m.width 37, input IN-4 and the cursor at the end, the View result contains no line break and its display width is at most 35.
- [ ] AC-3 (FR2): Under the AC-2 condition, the ANSI-stripped View result contains P-JA immediately followed by two PAIRs, and the pairing check reports no split pair.
- [ ] AC-4 (FR4): With P-JA and input IN-4, for every m.width 24..41 and every cursor position 0..8 (162 combinations, including positions on a U+FE0F rune), View does not panic, its result contains no line break, and its display width is at most m.width-2.
- [ ] AC-5 (FR5): With P-VS and an empty input, for every m.width 24..34 the View result contains no line break and its display width is at most m.width-2; at m.width 29 the ANSI-stripped result contains `(reverse-i-search)'` immediately followed by three PAIRs, and the pairing check reports no split pair.
- [ ] AC-6 (FR1, FR2, FR5; SPEC AC3, AC4): With a temporary change making the width-unit partitioning (partitionUnits) estimate each unit's width as the sum of its runes' own widths instead of measuring the unit's full text, the AC-3 check and the AC-5 m.width-29 content check fail; with that change plus a temporary change making the fit guard (guardFit) always return its first rendering unchanged, the AC-2 check fails (line break, or display width above 35). Both temporary changes are reverted so that `internal/ui/minibuffer.go` is identical to the base, are never committed, and the observed failures are recorded in the implementation report.
- [ ] AC-7 (NFR1, NFR2, NFR3): The committed change touches only `internal/ui/minibuffer_test.go` (go.mod and go.sum unchanged, no new dependency); the new tests are named `TestMinibufferView_{Scenario}` and use assertBoundedSingleLine, mustNotPanic and stripANSI; formatting with gofmt produces no diff; `go test ./...` passes in full.

## Test Notes

- All added tests are unit tests in the ui test package. TS-2 and TS-3 are
  table-driven with subtests, in the style of the existing width tables in
  this file (subtest names carry the width and the cursor position).
- Red phase: the current implementation already satisfies these behaviours,
  so the new tests pass on their first run against the base. AC-6's
  temporary changes supply the red evidence: apply each change, run the new
  tests, confirm the expected failures, then revert before committing.
- Only the premise check is fatal. The single-line and content checks are
  non-fatal so that, under AC-6, each failing check is reported separately
  (AC-6 must show the content check failing under the first change and the
  single-line check failing under the combined change).
- The cursor highlight wraps the rune under the cursor in its own escape
  sequence, so content checks operate on the ANSI-stripped text. In TS-1
  the cursor is at the end (trailing cursor block); TS-4 renders no input
  and no cursor highlight.
- In TS-2, cursor positions 1, 3, 5 and 7 sit on a U+FE0F rune (own width
  0); these positions are part of the required range.
- For review readability, write U+FE0F in a visible form (code-point
  notation) rather than as an invisible literal character.
