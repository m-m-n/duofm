# Task Plan: task0001 — Cancel the drag session on a successful directory load of the drag pane

## Goal

A successful directory load completion that replaces the entry list of the pane holding an armed or active mouse drag session resets that session to its initial (disarmed) state, so later motion and release events no longer apply the old list's anchor and baseline to the new list. Regression tests pin the behavior, including the cases that must leave the session untouched.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `internal/ui/model_update.go` — the directory load completion handler cancels the drag session on its success path when the completed pane is the drag session's pane
- `internal/ui/model_update_mouse_test.go` — regression tests for the five completion cases (TS-1 to TS-5)
- `internal/ui/model_update_mouse.go` — touched only if a small drag-session cancellation helper is co-located with the drag state machine; existing mouse handling does not change

## Design

### Defect being fixed

The directory load completion handler (handleDirectoryLoadComplete) replaces the target pane's entries, cursor and scroll offset but leaves the Model's drag session as it was. The session's anchor index and baseline mark snapshot were captured against the old list, so the next motion or release applies the old anchor range, on top of the old baseline, to the new list's entries and marks unintended files.

### Decision flow of the completion handler after the change

1. Resolve the target pane from the message's pane id (unchanged).
2. Stale completion — the target pane has a non-empty pending path that differs from the message's pane path: return without changes (unchanged). The drag session is not touched.
3. Clear the pane's loading state (unchanged).
4. Error completion — the message carries an error: run the existing error handling (previous path restore, pending cursor target clear, history restore, status message) and return (unchanged). The drag session is not touched.
5. Success completion: run the existing success processing unchanged (entry replacement with hidden-entry filtering, filter reset, cursor, scroll, pending path clear, git branch, history, disk space). Additionally, when the drag session is armed and its pane equals the completed pane, the drag session becomes its initial state.

### Cancellation contract

- Precondition: the success path has been reached (not stale, no error) and the target pane's entries have been replaced.
- Postcondition when the session is armed and belongs to the completed pane: the session is in its initial state — not armed, not active, no anchor, no baseline. The pane's current mark set is left exactly as it was at the moment of completion: it is neither restored to the press-time baseline nor cleared.
- Postcondition otherwise: the session is unchanged, field for field.
- "Armed" covers "active": the existing drag state machine only sets active on an armed session, so keying the cancellation on armed covers both states.
- Consequence: after cancellation, motion and release events are already ignored by the existing mouse handling until the next press (motion and release act only on an armed session). The mouse event handling itself needs no change.
- No existing statement on either the success or the error path is removed or reordered (NFR2).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS-1; FR1, FR5): With a left-pane session armed by a press on an entry (no motion), a successful completion for the left pane carrying a different entry list (no error; the left pane's pending path empty or equal to the message's pane path) leaves the drag session neither armed nor active; a subsequent motion to a different row and a release leave the left pane's mark set equal to the set captured immediately after the completion.
- [ ] AC-2 (TS-2; FR1, FR4, FR5): With a left-pane session made active by a press and a motion (a range already marked), a successful completion for the left pane with a different entry list keeps every mark present immediately before the completion (the mark set is not reverted to the press-time baseline) and leaves the session neither armed nor active; a subsequent motion to a different row and a release do not change the mark set.
- [ ] AC-3 (TS-3; FR2): With a left-pane session armed by a press, a successful completion for the right pane leaves the left session unchanged (still armed, same pane and anchor); a subsequent left-pane motion marks exactly the range from the original anchor to the motion row.
- [ ] AC-4 (TS-4; FR3): With a left-pane session armed by a press, a completion for the left pane that carries an error leaves the session unchanged; a subsequent motion marks exactly the range from the original anchor to the motion row.
- [ ] AC-5 (TS-5; FR3): With a left-pane session armed by a press and the left pane's pending path set to a non-empty path, a completion for the left pane whose pane path differs from that pending path leaves both the session and the left pane's entry list unchanged.
- [ ] AC-6 (FR5): The AC-1 and AC-2 tests fail against the handler without the cancellation (observed in the red step) and pass with it.
- [ ] AC-7 (NFR1, NFR2, NFR3): The full unit test suite passes, including every existing mouse, drag, double-click and directory-load test; the format command leaves no diff; go vet reports no findings.

## Test Notes

- All five scenarios are unit tests in the mouse test file, built on the existing two-pane mouse test model builder and its row and mouse-message helpers. Deliver both the mouse events and the completion message through the Model's update entry point so the message routing is exercised as well.
- Success-case completion message: the pane id of the pane under test, a pane path equal to that pane's current path (the builder's panes have an empty pending path), no error, and an entry list whose names do not occur in the pre-completion list and do not start with a dot (the success path filters hidden entries when the pane hides them).
- Give the new list enough entries that the post-completion motion row maps to an in-bounds index different from the anchor. Otherwise the pre-fix code would mark nothing on that motion and AC-6 would not hold.
- The success path moves the cursor and scroll offset to the top, so compute post-completion rows from scroll offset zero.
- Capture the pane's mark set right after the completion and compare it after motion and release with the existing marks-equality assertion helper.
- For AC-3 and AC-4, "the range from the original anchor" is asserted as an exact mark set: the pre-press marks plus the names between the anchor and the motion row inclusive, excluding the parent entry.
- Error case: the builder's panes have no previous path, so the error path's path restore is a no-op. The status message and the returned command are not asserted.
- Stale case: set the left pane's pending path to a non-empty path, send a completion with a different pane path, and compare the entry names before and after as well as the session.
- The success path also reads the git branch of the pane's path and refreshes disk space. The builder's temporary-directory panes support this; an existing message-type test already drives the success path in the same way.
