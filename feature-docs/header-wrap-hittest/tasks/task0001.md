# Task Plan: task0001 — Keep pane header line 1 on one row and share the header row count with the hit test

## Goal

Pane header line 1 always renders as one screen row that fits the pane
content width, in the normal, bg output split and dimmed views. The pane
header row count becomes one shared definition that the mouse hit test and the
renderer's visible-line computations both use. As a result, a mouse click,
drag or double-click acts on the entry drawn on the row the user clicked, even
when a directory outside git has a path longer than the pane width.

## Requirements

FR1, FR2, FR3, FR4, FR5, FR6, NFR1, NFR2, NFR3

## Scope

### Files to Create

None.

### Files to Modify

- `internal/ui/pane_render.go` — bound header line 1 to the content width on every branch (no branch, branch with truncated path, branch only); clamp widths so the ellipsis truncation never receives a negative width; derive the dimmed view's entry row count from the shared header row count
- `internal/ui/pane.go` — host the shared pane header row count definition; derive the normal-view visible line count and the bg-split heights from it
- `internal/ui/mouse_hittest.go` — derive the first entry row from the shared definition; remove the hit test's own header row literal
- `internal/ui/pane_render_test.go` — tests for header line 1 width bounds and the no-panic cases (AC-1, AC-2, AC-3)
- `internal/ui/mouse_hittest_test.go` — tests for the shared definition and for render / hit-test row alignment in all three views (AC-4, AC-5)
- `internal/ui/model_update_mouse_test.go` — Model-level click, drag and double-click tests with a long-path, no-branch pane (AC-6)

## Design

Cross-component contracts (the pane header row count, the header line 1
renderer, the ellipsis truncation) are pinned in IMPLEMENTATION.md "Shared
Components". This section covers only how this task satisfies them.

### Header line 1 (FR3, FR4, FR5, NFR2)

W = max(pane width − 4, 0). The composition order stays as it is today:
filter indicator, then the `[H]` indicator, then the display path (home
replaced by `~`).

1. Build the composed display string exactly as today.
2. **No git branch**: if the composed string's display width is ≤ W, return it
   unchanged. Otherwise return it truncated to W with the ellipsis truncation
   (head kept, ends with "...").
3. **Git branch present, everything fits**: unchanged — path, padding, then the
   bracketed branch right-aligned. The total equals W.
4. **Git branch present, path must shrink, path room ≥ 4**: unchanged —
   truncated path, at least one space, then the bracketed branch. The total
   stays ≤ W.
5. **Git branch present, path room < 4 (branch only)**: return the bracketed
   branch unchanged if its display width is ≤ W. Otherwise return it truncated
   to W with the ellipsis truncation (FR4).
6. Clamp every width computed on the way to 0 or more before passing it to the
   ellipsis truncation (FR5).

The ellipsis truncation itself also treats a negative width as 0, as a second
line of defence (IMPLEMENTATION.md contract). This covers the case where the
string is empty and the width is negative, which panics today.

### Shared header row count (FR6, NFR3, NFR1)

- Define the pane header row count once, in the pane layout file, next to the
  existing visible-line and bg-split height computations. Its value is 3.
- These consumers must reference it:
  - the hit test's first entry row (title row + 1 + header rows). The drag-row
    mapping uses the same first entry row, so it follows automatically.
  - the normal-view visible line count (pane height − header rows − 1 trailing
    row, minimum 1 as today)
  - the bg-split content height (same subtraction, existing clamps unchanged)
  - the dimmed view's entry row count (same subtraction, no new clamp)
- The hit-test file keeps no header row literal of its own. The existing
  hit-test-local name for the header row count is removed or defined in terms
  of the shared definition. The existing first-entry-row name that tests use
  stays available.
- Existing numbers do not change at any height (D3). Existing hit-test rules
  H1–H5 and drag clamping are untouched (A4).

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (TS-1, TS-2, TS-3; FR3, NFR2): With no git branch and pane width 40, header line 1 has a go-runewidth display width ≤ 36, contains no line break, and ends with "..." in each of these cases: (a) an ASCII path wider than the pane; (b) the same path with the hidden-files indicator and a filter indicator both applied; (c) a path containing full-width characters that is wider than the pane.
- [ ] AC-2 (TS-4; FR4): At pane width 15 with a git branch whose bracketed display is wider than 11 columns (the branch-only case), header line 1 has a display width ≤ 11 and contains no line break.
- [ ] AC-3 (TS-5; FR5): For every pane width from 0 to 4, with and without a git branch, header line 1 is produced without a panic and has display width 0. The ellipsis truncation with width 0 and with negative widths (including an empty input string) does not panic and returns a string of display width 0.
- [ ] AC-4 (FR6, NFR1, NFR3): The hit test's first entry row equals title row + 1 + the shared header row count (value 3). For pane heights 22 and 26: the normal-view visible line count and the bg-split file-list height are the values derived from the shared header row count plus one trailing row, and they equal the values before this change (for example, 18 visible lines at pane height 22). The dimmed view renders header rows + (pane height − header rows − 1) lines, not counting the empty piece after the final line break. `internal/ui/mouse_hittest.go` contains no header row literal of its own.
- [ ] AC-5 (TS-6; FR1, FR6, NFR3): For a pane with no git branch and a path wider than the pane, rendered in the normal view, the bg output split view and the dimmed view: the 0-based output line of the entry with index i (scroll offset 0) equals the shared header row count + i, and the hit test at screen row (title row + 1 + that line) returns an entry hit with index i. This test fails against the renderer as it was before this change.
- [ ] AC-6 (TS-7; FR1, FR2, FR3): In a Model at 80x24 whose left pane shows a no-branch directory with a path wider than the pane, rows are located in the rendered output. A left press and release on the row of entry i moves the cursor to i. A drag from the row of entry a to the row of entry b marks exactly the entries a through b, excluding the parent-dir entry. A double-click on the row of a subdirectory entry starts the Enter action for that subdirectory, with the same observable result the existing double-click tests assert.
- [ ] AC-7 (TS-8; NFR1): All existing tests in `internal/ui` still pass without being edited, including the header line 1 cases where the path fits, the cases with a branch, and the existing hit-test / mouse / drag tests. The project test command also passes.

## Test Notes

- AC-1 to AC-3 go in `internal/ui/pane_render_test.go`, using pane literals as
  the existing header line 1 tests do. Assert display width with go-runewidth
  and check for the absence of line breaks. Do not assert exact strings,
  except where an existing test already fixes them.
- AC-4 and AC-5 go in `internal/ui/mouse_hittest_test.go`. For AC-5:
  - Build the pane over a temp directory nested deeply enough that the
    displayed path is wider than the pane whatever the temp root is. Set the
    pane's git branch to empty after creating it, so the test does not depend
    on whether the temp root is inside a git repository.
  - Remove ANSI escape sequences before splitting the output into lines.
  - Locate entries by unique file names. Do not locate the parent-dir entry
    "..", because the truncated header ends with "...", which also contains
    "..".
- AC-6 goes in `internal/ui/model_update_mouse_test.go`:
  - Find the target screen row from the rendered screen. Do not use the
    existing row helper, which is derived from the hit-test constant. Finding
    the row from the screen is what makes this test detect a
    renderer / hit-test mismatch.
  - Render the Model's own view if the test Model can be given the
    collaborators it needs. Otherwise, use the pane's normal view offset by the
    title row.
  - For the double-click, reuse the fake-clock detector pattern of the
    existing double-click tests.
- Red phase: confirm that the AC-5 and AC-6 tests fail on the renderer as it
  was before the fix (entries appear one row lower than the hit test expects),
  then implement. SPEC.md AC6 requires this.
- Regression (AC-7): run the whole `internal/ui` package, not only the new
  tests. The existing mouse tests assume first entry row 4 and 18 visible
  lines at 80x24.
