# Task Plan: task0001 — Linear-time Minibuffer.View range selection with regression tests

## Goal

Minibuffer.View finishes in time linear in prompt length + input length on
every path (cursor at the end, cursor elsewhere, prompt truncation) and keeps
its existing postconditions; `internal/ui/minibuffer_test.go` gains
time-bound regression tests (TS-1..TS-4) and a guard test (TS-7).

## Design

Terms follow IMPLEMENTATION.md: width basis and own width (Conventions),
width unit (CD2), segment (CD3), guard (CD4). Below, content width is
m.width - 4 and remaining is content width minus the prompt width.

### Flow of one View call

1. Not visible: return the empty string (unchanged).
2. Content width at most 0: render the empty content line with the existing
   style (unchanged narrow-width behaviour).
3. Measure the prompt width once (width basis on the whole prompt).
4. Prompt width at least the content width (prompt-truncation path):
   1. Partition the prompt into width units in one pass.
   2. Keep the longest unit prefix whose estimated width is at most the
      content width.
   3. Apply the guard to the kept prompt. Input and cursor are not rendered.
5. Otherwise (remaining at least 1):
   1. Fit check: assemble the full line (prompt + whole input with the cursor
      highlight, or with the cursor block when the cursor is at the end) once
      and measure it once. If it is at most the content width, render it
      untruncated and stop.
   2. Cursor at the end: partition the whole input into units; keep the
      longest unit suffix whose estimated width is at most remaining - 1 (the
      cursor block takes 1 column).
   3. Cursor not at the end and the cursor rune's own width exceeds
      remaining: render no input (unchanged).
   4. Cursor not at the end and the estimated width of every unit before the
      cursor plus the cursor rune's own width is at most remaining: the
      window starts at the input start and extends right over the longest
      unit prefix of the after-cursor segment that fits the leftover width.
   5. Otherwise: the window ends right after the cursor rune and starts at
      the longest unit suffix of the before-cursor segment that fits
      remaining minus the cursor rune's own width.
   6. Assemble the chosen window once and measure it once. If it exceeds the
      content width, apply the guard. The side away from the cursor is the
      left side for steps 5.2 and 5.5, and the right side first, then the
      left side, for step 5.4.
6. Apply the existing line style once to the final content line.

### Helper contracts (names at the implementer's discretion)

- **Unit partition** — input: one segment as a rune sequence. Output: an
  ordered list of units, each with start/end rune offsets within the segment
  and an estimated width. Postconditions: units are contiguous, do not
  overlap, and cover the whole segment; every unit except possibly the first
  starts with a positive-own-width rune; each rune's own width and each unit's
  width is measured exactly once; running time is linear in the segment
  length.
- **Longest prefix / longest suffix** — input: a unit list and a width
  budget. Output: how many units are kept from the front (or from the back).
  Postconditions: the kept estimates sum to at most the budget; keeping the
  next unit would exceed it; one pass over the units.
- **Guard** — input: the candidate window (or kept prompt) and its measured
  excess. Output: the final window. Postconditions: as CD4; at most 3
  re-measurements; the cursor's own rune is never trimmed except by the
  final "no input" fallback.

### Behaviour notes

- The cursor rune's own width still decides step 5.3, as before.
- A cursor on a zero-width rune is highlighted as before (it occupies no
  visible cell).
- Display content differs from the pre-change output only where the old
  per-rune boundary fell inside a unit (FR2).

## Test Notes

- **TDD order**: write TS-1..TS-4 first and run them against the unchanged
  View to capture AC-3's red result. Prefer running only the tests whose
  names start with `TestMinibufferView_LinearTime`; the pre-change View keeps
  burning CPU in the abandoned goroutines. If only the full project test
  command is available, it also works: the four tests fail at 10 seconds each
  and the rest of the package completes more slowly.
- **Goroutine pattern**: View runs in its own goroutine and hands its result
  back to the test; the test waits for either the result or the 10-second
  limit. A panic inside the goroutine should be caught and reported as a test
  failure rather than crash the test binary.
- **Duration logging**: log View's elapsed time so verbose output shows it for
  TS-6.
- **Fixture self-checks** (same style as the existing "test fixture
  assumption broken" checks): the width of U+00A9 U+FE0F is 2 while its
  per-rune sum is 1; TS-7's width gap (1 + 1 < 3).
- **Rendering environment**: tests run without a color profile, so highlight
  and style sequences are normally absent. Assertions must rely on the
  ANSI-stripped text and on the width basis applied to the whole result, never
  on escape sequences being present.
- **Recommended extra (not an AC)**: a long zero-width run inside the
  displayed window (for example 'a' followed by U+0301 x100000, cursor at the
  end, m.width 40) exercises the fit path and the final style application on a
  long line.
- **Existing tests that pin related behaviour** and must pass unchanged:
  BoundaryWidths (prompt truncation content), ScrolledInput_CursorCharacterVisible
  (cursor rune visible while scrolling), the ZWJ tests (untruncated fit judged
  by the actual width; the "ls" tail visible when scrolling), NarrowWidths
  (widths 0-4).
