# Task Plan: task0001 — Grapheme-wise cursor movement and whole-grapheme cursor highlight

## Goal

Left/Ctrl+B and Right/Ctrl+F move the minibuffer cursor one grapheme cluster at a time, and View renders the whole cluster containing the cursor as a single reversed segment on the fit path and on every scroll path, so a cursor inside a joined sequence never splits it and an input that fits is never truncated.

## Requirements

FR1, FR2, FR3, FR4, FR5, NFR1, NFR2, NFR3, NFR4

## Scope

### Files to Create

None.

### Files to Modify

- `internal/ui/minibuffer.go` — add the grapheme cluster locator; switch the four movement keys to cluster bounds; revise the line builder to highlight a range; use the cursor's cluster in the fit check and in steps 3, 4 and 5 of View
- `internal/ui/minibuffer_test.go` — regression tests for AC-1 to AC-8, the 256-color profile helper and the reversed-run extraction helper
- `go.mod` — rivo/uniseg becomes a direct requirement at the same version
- `go.sum` — touched only if the Go toolchain requires it for the promotion above; expected to stay unchanged

## Design

Cross-task decisions GD1–GD5, the position/width/segmentation conventions, and the grapheme cluster locator's contract are in IMPLEMENTATION.md; they are referenced here, not restated.

### Grapheme cluster locator

A private function in minibuffer.go implementing the Shared Components contract in IMPLEMENTATION.md. It is the only place that talks to rivo/uniseg.

### Cursor movement (HandleKey)

- **Left and Ctrl+B** (identical behavior): when cursorPos > 0, cursorPos becomes the start of the cluster containing rune cursorPos − 1. This single rule covers both cases of FR1: at a cluster start the cursor moves to the previous cluster's start; inside a cluster it moves to its own cluster's start. At position 0 nothing changes.
- **Right and Ctrl+F** (identical behavior): when cursorPos < rune count, cursorPos becomes the end of the cluster containing rune cursorPos. At the end nothing changes.
- The keys still report "handled". Every other key's behavior is unchanged (GD4).

Worked example with familyEmojiLsInput (family emoji = runes 0..6, "l" = 7, "s" = 8, end = 9): Left from 9 gives 8, 7, 0; Right from 0 gives 7, 8, 9; from any k in 1..6, Left gives 0 and Right gives 7.

### Line builder (existing buildLine), revised contract

- **Inputs**: the displayed runes D (a contiguous slice of the input) and highlight bounds (hs, he) relative to D.
- **hs negative**: no highlight (same meaning as today's "no highlight" sentinel).
- **0 <= hs < he <= length of D**: the runes D[hs, he) are rendered as ONE reversed segment (a single reverse-styled rendering of their concatenated text); all other runes are written plain.
- **hs equal to the length of D**: the trailing block cursor (reversed single space), unchanged.
- **Precondition**: when a range is given, it is the cursor cluster's bounds translated into D's coordinates; the builder itself never segments.

### View

Let n be the input's rune count. When cursorPos < n, let [gs, ge) be the locator's result for cursorPos (computed once per View call) and cw the width-basis measurement of the cluster text runes[gs, ge) (measured once).

Unchanged paths: content width <= 0; prompt truncation (prompt width >= content width); step 2 (cursor at the end).

1. **Step 1, fit check (FR2, FR3)**: the full line is the prompt plus the line builder over the whole input with highlight [gs, ge), or with the block cursor when the cursor is at the end. It is assembled and measured once; if it fits the content width, the whole input is rendered with that highlight.
2. **Step 3 (FR4)**: the "cursor does not fit even alone" condition compares cw, not the cursor rune's own width, against the remaining width. When cw exceeds it, no input is rendered (same outcome as today).
3. **Steps 4 and 5 (FR4)**:
   - The before-cursor segment is runes[0, gs) and the after-cursor segment is runes[ge, n); each is partitioned into width units exactly as today. The cursor's width contribution is cw.
   - Where the code today uses "cursor + 1" as the window end (no after-units kept in step 4; always in step 5), it uses ge. Where it uses "cursor" as the fallback window start (all before-units dropped), it uses gs.
   - The highlight passed to the line builder is [gs − window start, ge − window start).
   - The fit guard's shrink steps still remove whole width units only from the before and after segments, so [gs, ge) is never cut. If the guard gives up, no input is rendered (existing behavior).
4. **Window edge away from the cursor**: unchanged width-unit trimming (GD3).
5. **Comments**: update the wording of View and line-builder comments that describe "the cursor rune/character" where the behavior now concerns the cursor's cluster. Existing citations of CD2–CD5 stay.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (FR1; SPEC AC1, AC2; TS1, TS2): With familyEmojiLsInput, starting from cursor 9, three Left presses give cursorPos 8, 7, 0 in that order, and three Ctrl+B presses give the same. Starting from cursor 0, three Right presses give 7, 8, 9, and three Ctrl+F presses give the same. A further Left/Ctrl+B at 0 and Right/Ctrl+F at 9 leave cursorPos unchanged.
- [ ] AC-2 (FR1; SPEC AC3, AC4; TS3, TS4): After SetCursorPos(k) on familyEmojiLsInput for each k in 1..6, Left and Ctrl+B give 0 and Right and Ctrl+F give 7. For inputs containing e + U+0301, U+2764 U+FE0F, a flag pair U+1F1EF U+1F1F5, and a leading isolated zero-width rune (a combining mark, and separately a ZWJ, at the input start followed by ASCII letters), every Left/Right press moves the cursor across exactly one grapheme cluster, with the expected positions written out explicitly in a table-driven test. On an empty input all four movement keys leave cursorPos at 0.
- [ ] AC-3 (FR2; SPEC AC5, AC6; TS5): With the renderer's color profile fixed to 256 colors, searchPrompt, familyEmojiLsInput and a width at which the whole line fits (m.width 19 or more): for every cursor 0..6 the View output contains exactly one reversed run, that run contains all 7 family-emoji runes contiguously, and no family-emoji rune appears outside it; for cursor 7 the only reversed run is "l"; for cursor 8 it is "s"; for cursor 9 it is a single space (block cursor unchanged). Reproduction: after entering the family emoji through key input and moving Left one press at a time to position 0 and then Right back to the end, at every step the ANSI-stripped output contains the whole family emoji and the emoji never straddles a reversed-run boundary.
- [ ] AC-4 (FR3; SPEC AC7; TS6): With the 256-color profile fixed, searchPrompt and familyEmojiLsInput, for every m.width 19..24 and every cursor 1..6, the ANSI-stripped output contains searchPrompt immediately followed by the whole input.
- [ ] AC-5 (FR4; SPEC AC8; TS7): With the 256-color profile fixed, searchPrompt and familyEmojiLsInput, for every m.width 14..18 and every cursor 0..6, either the family emoji appears whole inside a single reversed run or none of its runes appear in the output. At m.width 15 (the emoji's width exceeds the remaining width) no input rune is rendered.
- [ ] AC-6 (NFR1; SPEC AC9; TS8): All existing bounded-single-line tables still pass, and new tables whose inputs contain flag pairs, e + U+0301 sequences, and a leading isolated zero-width rune pass assertBoundedSingleLine for every m.width 10..30 with searchPrompt and every cursor position 0..n, under both the default profile and the fixed 256-color profile.
- [ ] AC-7 (FR2, FR5; SPEC AC10; TS9): On familyEmojiLsInput with cursor 3: Backspace removes exactly rune 2 and leaves cursorPos 2; Delete removes exactly rune 3 and leaves cursorPos 3; inserting one rune places it at index 3 and leaves cursorPos 4; Ctrl+K keeps exactly runes 0..2; Ctrl+U keeps runes 3..8 and sets cursorPos 0. When an insertion leaves the cursor inside a cluster, the single reversed run in the next View (256-color profile) is that whole cluster. Ctrl+A, Ctrl+E, SetInput, SetCursorPos and CursorPos behave as before.
- [ ] AC-8 (NFR2, NFR3, NFR4; SPEC AC11, AC12; TS10): Every pre-existing test in internal/ui/minibuffer_test.go (including the linear-time TS1–TS4 and TS7 tests) passes without its assertions being weakened; go test ./... and go vet ./... succeed; gofmt reports no difference; go.mod lists rivo/uniseg v0.4.7 as a direct requirement, and no other requirement is added, removed or re-versioned.

## Test Notes

- All criteria are unit tests in internal/ui/minibuffer_test.go (SPEC A6: no E2E test). Reuse the existing fixtures and helpers: familyEmojiLsInput, searchPrompt, the family-emoji fixture premise check, assertBoundedSingleLine, the panic-guarding View wrapper and the ANSI-stripping helper.
- **256-color profile helper**: a test helper that fixes the default renderer's color profile to 256 colors and registers restoration of the previous profile at test cleanup. Tests using it do not run in parallel. It first asserts, fatally, that rendering a sample character with the reverse attribute yields an escape sequence under the fixed profile. Without this, a non-terminal test run emits no escape sequence for the reverse attribute, so AC-3, AC-4 and AC-5 would pass vacuously on the unfixed code (the split highlight would neither inflate the measured width nor be visible as a separate reversed run).
- **Reversed-run extraction helper**: returns, in order, the texts rendered while the reverse attribute is on in a View result. The outer minibuffer style also emits color escape sequences (including extended-color parameter lists); these must not be mistaken for the reverse attribute being switched on or off.
- **Expected red phase** (before the change): AC-1 and AC-2 fail (movement is rune-wise); AC-3 fails (a single rune is reversed); AC-4 fails for at least some width/cursor combinations (the split highlight inflates the measured width and the scroll path truncates); AC-5 fails at m.width 16 and 17 (partial emoji runes are rendered). AC-6, AC-7 (except the insertion-highlight clause) and AC-8 are guard rails that pass both before and after.
- **Illustrative fixtures** (the implementer may choose equivalents): "e" + U+0301 + "x" (clusters of 2 and 1 runes); U+2764 U+FE0F + "x"; "a" + U+1F1EF U+1F1F5 + "b"; U+0301 + "ab" and U+200D + "ab" (the leading zero-width rune is its own cluster); for the insertion clause of AC-7, input "e" + U+0301 with cursor 1, insert "a" — the cursor (2) lands inside the cluster "a" + U+0301, which must be reversed as a whole.
- Edge cases to cover explicitly: empty input; cursor at start and at end; SetCursorPos inside a cluster (the tab-completion path); step 3 at m.width 15; steps 4 and 5 at m.width 16 and 17.
- The existing linear-time tests are the NFR3 gate; no new timing test is required.

## Out of Scope

- Deleting or inserting by grapheme cluster (Backspace, Delete, Ctrl+K, Ctrl+U stay rune-wise — GD4)
- Word-wise movement, or any change to Ctrl+A, Ctrl+E, SetInput, SetCursorPos or CursorPos
- Aligning the window edge away from the cursor to cluster boundaries (GD3, SPEC A4)
- The prompt-truncation path, the content-width <= 0 path and step 2 (cursor at the end)
- Changing the highlight's appearance or the trailing block cursor (SPEC A7)
- Tab completion (model_update_keyboard.go) or any file outside the Files list
- E2E tests, and other text inputs elsewhere in the application
