# Task Plan: task0001 — Keep runner self-test temporary files inside SELF_TMPDIR and add regression scenario TS-6

## Goal

The runner self-test's fixture-list helper (apply_fixture_lists) creates its intermediate temporary files inside the self-test's own temporary directory SELF_TMPDIR instead of the environment's temporary directory, and a new self-test scenario TS-6 fails whenever either of those files is created outside SELF_TMPDIR again.

## Design

### 1. Intermediate-file location in apply_fixture_lists (FR1)

Current behavior: each of the two list-rewrite steps (TEST_FILES first, then FULL_RUN_LIST) writes the rewritten runner copy to a uniquely named intermediate file and then moves that file over the runner copy. The intermediate file's directory is taken from the environment (TMPDIR, falling back to the system temporary directory), so it lives outside SELF_TMPDIR. When the rewrite or the move fails, the file is orphaned there.

Required behavior:

- Both intermediate files are created with unique names inside SELF_TMPDIR. The directory is supplied explicitly, so the location depends neither on the TMPDIR value in effect at call time nor on the runner-copy argument.
- The files are placed directly in SELF_TMPDIR, not in a directory derived from the runner-copy path, so creation still succeeds when the runner-copy path does not exist.

Unchanged contract of apply_fixture_lists:

| Aspect | Contract (unchanged) |
|---|---|
| Inputs | runner-copy path, TEST_FILES body text, FULL_RUN_LIST body text |
| List replacement | each list literal's body is replaced with the given text; the move over the runner copy happens only when that rewrite step succeeded |
| Executable bit | restored on the runner copy after both rewrites, as now; the explanatory comment next to it stays accurate |
| Return value | 1 when a production-only entry is still present in the runner copy (fail closed), 0 otherwise; the helper never exits the script |

Cleanup: no per-call cleanup is added. An intermediate file orphaned by a mid-way failure stays inside SELF_TMPDIR and is removed with it by the existing EXIT trap (cleanup_self_tmpdir).

- Precondition: SELF_TMPDIR exists (it is created at script start, before any scenario runs).
- Postcondition: no file or directory created by apply_fixture_lists exists outside SELF_TMPDIR at any time, whatever TMPDIR value is in effect when it is called.

### 2. Scenario TS-6 (FR2)

Processing flow:

1. Create a TS-6 scenario directory under SELF_TMPDIR, following the per-scenario directory convention of the existing scenarios, and an empty sentinel directory inside it.
2. Export the sentinel directory as TMPDIR for the remainder of the scenario.
3. Call apply_fixture_lists with a runner-copy path under the TS-6 scenario directory that is never created, together with any fixture list bodies.
4. Both rewrite steps create their intermediate file and then fail because the input file does not exist; no move happens. The helper returns 0 on this path (SPEC.md Notes), so its return value is not asserted.
5. Check the sentinel directory: the scenario passes only when the sentinel still exists and contains no entries, hidden entries included. Otherwise it prints a diagnostic naming each leftover entry (or stating that the sentinel is missing) and returns non-zero.
6. main runs TS-6 through run_scenario after TS-5, with a one-line description. run_scenario prints the PASS/FAIL line and sets OVERALL_STATUS on failure.

Design constraints:

- The forced failure hits both rewrite steps, so a regression at either creation site alone leaves an entry in the sentinel directory. TS-6 therefore guards both sites.
- The sentinel directory is distinct from the place where apply_fixture_lists puts its intermediate files: it is a subdirectory of the TS-6 scenario directory, never SELF_TMPDIR itself. Otherwise the fixed code would also populate it.
- The TMPDIR override is confined to TS-6. It does not change TMPDIR for the main script or for any other scenario. SELF_TMPDIR was created before any override and is unaffected by it.
- TS-6 does not execute the runner copy, and starts no tmux session and no duofm process (NFR2).
- Everything TS-6 creates lives under SELF_TMPDIR (NFR1).
- Diagnostics the failing helper prints (missing input file and similar) may be suppressed inside TS-6 or left as they are; run_scenario shows scenario output only on FAIL.

### 3. Header comment (SPEC.md A-4)

The header's scenario range (currently "Scenarios TS-1 through TS-5 ...") is extended to cover TS-6. The header's write-scope promise stays as written; this task makes it true.

- [ ] AC-5 (NFR1, NFR2): TS-6's sentinel directory and runner-copy path are under SELF_TMPDIR; its TMPDIR override does not persist beyond TS-6; TS-6 executes no runner copy and starts no tmux session and no duofm process.

## Test Notes

- The test vehicle for this task is the self-test itself. TS-6 is the regression test for FR1, and TS-1 to TS-5 guard the unchanged contract of apply_fixture_lists. No separate test file is added.
- TDD order: add TS-6 first and run the self-test against the unmodified apply_fixture_lists. TS-6 must FAIL there, because the defect leaves intermediate files in the sentinel directory. Only then relocate the intermediate files and confirm TS-6 passes. A TS-6 that already passes before the fix does not observe the defect and must be reworked.
- AC-4 is a mutation check: revert each creation site separately, run the self-test, confirm the TS-6 FAIL line and the non-zero exit, then restore. Leave the working tree without any mutation.
- AC-5's confinement of the TMPDIR override is checked by inspection of how TS-6 scopes it (set only within the scenario's own execution context), together with TS-1 to TS-5 and the rest of the run behaving as before.
- A whole-run check for NFR1 is useful but optional here: run the full self-test with TMPDIR pointing at a fresh empty directory; after the script exits, that directory must be empty.
- The container half of the regression (E2E image default command, non-root user) is exercised in the verify phase through the project's E2E command; the implementer is not required to run it.
